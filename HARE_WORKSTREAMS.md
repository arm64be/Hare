# Hare Workstreams

This document separates judgment-heavy work from mechanically parallelizable
work. The latter is the requested "slave labour" bucket; the project uses the
term mechanical lane so task descriptions remain precise.

The split is about authority, not difficulty. Mechanical work may be large and
technical, but its correctness must be decidable from an existing contract.
Judgment work creates or changes that contract.

## Judgment Lane

Judgment work stays with the architect/integrator until it has been reduced to
a testable specification.

Examples:

- JavaScript semantic boundaries and compatibility promises
- JSC bytecode extraction point and versioning
- Hare IR semantics and validation rules
- runtime ABI, calling conventions, and value representations
- GC roots, write barriers, safepoints, and pinning
- exception scopes, re-entry, and deoptimization state
- MutMem soundness rules and proof-manifest trust boundaries
- Effect laziness, interruption, scopes, finalizers, and scheduling semantics
- Result layout and backtrace materialization
- LLVM versioning, target layout, LTO, and PGO policy
- public CLI and build API design
- acceptance or rejection of performance and memory tradeoffs
- upstream synchronization and conflict resolution

Judgment-lane outputs must be durable artifacts:

- an accepted decision in `HARE.md` or a focused RFC
- an input/output schema
- invariants and explicit non-goals
- at least one positive and one adversarial example
- an executable verification command
- a task decomposition with non-overlapping path ownership

No worker should infer architecture from a vague goal such as "make this
native" or "optimize this opcode."

## Mechanical Lane

Mechanical work starts only after the judgment lane supplies a closed contract.

Good mechanical tasks:

- inventory JSC opcodes from generated bytecode definitions
- generate Rust enums or tables from a pinned schema
- add fixtures for an assigned opcode family
- implement repeated lowering handlers from an approved template
- add IR parser, printer, validator, and snapshot cases from a specification
- scaffold Cargo crates and build graph entries
- port source-location and function-identity metadata through known structures
- add CLI plumbing after the option and semantics are fixed
- collect reproducible baseline results
- run differential corpora and minimize failures
- fix compiler errors within one owned crate without changing its public contract
- add platform implementations after the reference platform is accepted
- update generated documentation and compatibility matrices

Mechanical workers must escalate rather than improvise when:

- an unsafe block or new FFI precondition is needed
- a JSC object survives a call, allocation, callback, or safepoint
- a bytecode has semantics missing from the task contract
- a test oracle disagrees with JSC
- a public type, manifest, IR, or ABI needs to change
- a borrow might escape, alias, suspend, or re-enter
- fallback state cannot be reconstructed exactly
- the proposed fix weakens validation or deletes an adversarial case
- performance changes depend on unmeasured assumptions

## Four-Worker Loop

The initial execution loop fits four concurrent workers:

| Role | Responsibility |
| --- | --- |
| Architect/integrator | Own contracts, dispatch, merges, full builds, and final decisions |
| Implementer | Complete one bounded task in an isolated worktree |
| Adversarial reviewer A | Look for semantic, memory, GC, exception, and ownership failures |
| Adversarial reviewer B | Look for test gaps, platform failures, build coupling, and false performance claims |

After both reviews, the implementer or a dedicated fixer applies only accepted
findings. Roles rotate between tasks so an implementer does not approve its own
reasoning.

The reviewers receive the task contract and diff. They do not receive the
implementer's rationale until after their independent reports. This prevents a
plausible explanation from becoming the test oracle.

## Task Lifecycle

1. The architect changes a task in `HARE_TASKS.tsv` from `blocked` to `ready`
   only after its contract and verification command exist.
2. The implementer creates an isolated worktree and branch for exactly one task.
3. The implementer runs the narrowest useful checks and commits the bounded diff.
4. Two reviewers independently attempt to disprove correctness.
5. The fixer addresses accepted findings and adds regression coverage.
6. The integrator runs crate checks, focused Bun tests, and conflict checks.
7. Only the integrator runs a full `bun bd` or timing-sensitive benchmark.
8. The task becomes `done` only after its exit condition is recorded.

Task statuses:

| Status | Meaning |
| --- | --- |
| `blocked` | Missing an upstream artifact or judgment decision |
| `ready` | Fully specified and safe to claim |
| `active` | Owned by exactly one implementation worktree |
| `review` | Implementation committed; no further scope changes |
| `fix` | Accepted review findings are being addressed |
| `integrate` | Reviews are clear; integration verification remains |
| `done` | Verification and required artifacts are recorded |

## Repository Rules

- Branches use `claude/hare-<task-id>-<slug>`.
- Each task owns an explicit path set. Two active tasks never own the same file.
- Never use `git stash`, `git reset`, destructive checkout, or force push.
- Do not mix upstream synchronization with feature work.
- Commit only task-owned files. Do not "clean up" neighboring code.
- Generated output is changed through its generator when one exists.
- Commit messages describe verified behavior, not intended behavior.
- A worker that encounters an unrelated failure records it and continues unless
  it invalidates the task's oracle.
- Unsafe, FFI, GC, exception, and ABI changes always require judgment review.
- No broad formatting pass while functional work is in flight.

## Build Scheduling

Bun and WebKit builds are expensive and can invalidate benchmark results. The
integrator owns a build token:

- workers may run parser-only tests and `cargo check -p <owned-crate>`
- only one worker runs `bun bd` at a time
- only one worker builds local WebKit at a time
- benchmarks run in an announced quiet window
- no other worker compiles Rust, C++, WebKit, or a large dependency during that
  window
- raw results are saved before interpretation

The integration worktree keeps the reusable build cache. Task worktrees should
not duplicate WebKit or dependency trees; use the build system's supported
shared paths and caches.

## Review Prompts

### Adversarial Semantics Review

Assume the implementation is wrong. Find the smallest input that causes its
native behavior to differ from JSC. Check coercion, overflow, `NaN`, negative
zero, getters, proxies, exceptions, re-entry, detached buffers, GC, and source
locations where relevant.

### Adversarial Ownership Review

Assume every reference aliases and every callback re-enters. Trace values across
branches, loops, closures, unknown calls, suspension, throws, deoptimization,
and GC. Reject any proof that relies only on a TypeScript type.

### Adversarial Performance Review

Assume the reported gain is noise or displaced work. Check warmup, sample count,
fallback rate, binary size, RSS, allocations, build time, machine contention,
and whether the baseline performs the same observable work.

### Mechanical Equivalence Review

Compare the generated table, handler, fixture, or port against its source of
truth entry by entry. Look for omissions, duplicate identifiers, width/sign
errors, stale generated output, and accidental changes outside the owned paths.

## Initial Ownership Boundaries

These boundaries minimize conflicts during the first milestones:

| Area | Initial owner | Notes |
| --- | --- | --- |
| `src/jsc/bindings/` bytecode bridge | Judgment lane | JSC lifetime and exception boundary |
| `src/jsc/` Rust bridge | Judgment lane | Safe wrapper around the C++ extraction API |
| new Hare IR crate | Mechanical after RFC | Parser/printer/validator can be sharded by module |
| new Hare LLVM crate | Judgment lane | LLVM ABI, data layout, and ownership of values |
| `src/bundler/` metadata | Judgment lane first | Function IDs and proof manifest contract |
| opcode fixtures | Mechanical lane | Shard by opcode family |
| differential tests | Mechanical lane | Shard by semantic family, shared harness owned centrally |
| `src/runtime/cli/` native flags | Mechanical after RFC | No provisional public flags before M3 |
| build and linker scripts | Judgment lane | LTO and PGO compatibility |
| benchmark corpus | Mechanical lane | Harness design and acceptance thresholds stay judgment-owned |

## What We Copy From The Bun Rewrite

We deliberately copy the useful process, not the headline scale:

- serialize architectural knowledge before mass implementation
- make compiler errors and failing tests explicit work queues
- use bounded implementer/reviewer/fixer loops
- give adversarial reviewers separate context
- make every worker commit a narrow, attributable change
- repair the process that generated a class of defects, not only one instance
- preserve the existing test oracle while changing implementation language or tier

We do not begin with hundreds of parallel edits. Parallelism increases only
after M1 produces a stable schema and M2 produces a validated IR contract.
Before those gates, more workers create conflicting guesses rather than useful
throughput.
